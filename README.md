# StreetLab

A self-driving simulator I built solo: a native desktop app that drives a
car through real OpenStreetMap city streets, with a from-scratch physics
sim, a reactive traffic model, and a real computer-vision detector running
in the loop. **A portfolio/learning project, not a production AV system** —
none of the numbers below are safety claims.

## What this is

Point it at any real address and it geocodes the location, pulls the actual
street and building layout from OpenStreetMap, and drives a simulated car
through it — obeying traffic lights and stop signs, reacting to other
traffic, and reporting live telemetry (FPS, tick rate, sim latency, memory)
pulled from the real running processes, not canned demo data. A GPU-rendered
3D viewport, a physics/traffic simulator, and an ONNX-based vehicle detector
all run together over a schema-validated WebSocket link, packaged as a
double-click-to-run native app.

I built this to go deep on the kind of problems that come up in real-time
graphics, simulation, and applied ML systems: a GPU rendering pipeline, a
deterministic real-time simulation loop, a computer-vision model integrated
end-to-end (not just trained in a notebook), and — closest to how I'd want
to work as an SA — treating every performance and accuracy claim as
something to measure, not assume. The [Results](#results) section below is
the clearest example: it walks through a real int8-vs-fp32 quantization
comparison, including a rendering bug that had silently corrupted the first
round of measurements.

## Highlights

- **Real-time 3D rendering** — Three.js over WebGPU (WebGL2 fallback), 30–60 FPS
- **Native desktop app** — Rust/Tauri shell wrapping the UI and managing the
  Python simulation process as a sidecar, zero-config `.app` bundle
- **Deterministic simulation engine** — kinematic vehicle model, IDM
  car-following, MOBIL lane-changing, a signal/stop-sign FSM, all driven by a
  fixed-step Python loop
- **Real-world map data** — live geocoding + OpenStreetMap ingest (Overpass
  API), cached for offline use, built off the render thread so the car never
  stutters while a new city block loads
- **ML inference in the loop** — a real RT-DETR ONNX object detector
  processing camera frames from the simulator, with 2D→3D tracking and
  scoring against ground truth
- **Schema-enforced client/server contract** — every WebSocket message is
  validated against the same schema on both the TypeScript (zod) and Python
  (pydantic) sides, from fixtures generated by the real simulation
- **1,100+ automated tests** — 910 backend (pytest), 205 frontend (vitest),
  12 end-to-end (Playwright), all green

## Architecture

```
┌─────────────────────────┐   ws://…    ┌──────────────────────────┐
│  streetlab/ (frontend)   │◀───────────▶│  streetlab-backend/      │
│  Tauri + React + Three   │             │  (Python, uv-managed)    │
│                          │  GET /health │                          │
│  wsClient.ts ──────────────────────────▶  server/ws_server.py     │
│  (or the in-process       │            │  server/cli.py            │
│   mock, for offline dev)  │            │  sim/{loop,agents,route}  │
└─────────────────────────┘             │  map/scene_build.py       │
                                          │  perception/service.py   │
                                          │  plan/control.py         │
                                          └──────────────────────────┘
```

Two independently-tested packages, wired together over a WebSocket, plus a
shared **contract** package (`contract/`) that generates fixtures from the
real simulation and validates them against both the TypeScript and Python
schemas — so a breaking field rename or type change fails CI on both sides,
not just one.

## Results

The part of this project most relevant to solutions/applied-ML work: every
performance number here comes from a measurement I ran and can reproduce,
including the ones that didn't go the way I expected.

- **The detector, run honestly, sees zero vehicles.** A real RT-DETR ONNX
  model runs on live camera frames from the simulator and is scored against
  exact ground truth. On this renderer's imagery, at the production
  confidence threshold, it detects **zero vehicles** — a real domain-gap
  finding, not a bug (the low-poly geometry doesn't look like COCO's photos).
- **I found and fixed a measurement bug before trusting the result.** The
  detector's camera path was missing tone-mapping/sRGB encoding — a Three.js
  render-target bug — meaning every earlier detector frame was raw linear
  data. I fixed it and re-ran the comparison; the zero-detections finding
  held, but only after the measurement itself was verified correct.
- **Quantization tradeoff, measured, not assumed.** I benchmarked the
  shipped int8 model against fp32 of the same architecture: fp32 lifts peak
  detection confidence **~2.6×** but the underlying zero-detections result at
  the production threshold doesn't change — and CPU inference measured **4×
  faster than CoreML** for this model, which is why the sidecar runs on
  `CPUExecutionProvider`. Full numbers in
  [`docs/measurements/`](docs/measurements/).
- **Fine-tuning was tried and reported as a null result.** I built the full
  capture → label → train → export → evaluate pipeline, ran it on 12 real
  captures (3,430 labeled boxes), and the fine-tuned checkpoint scored
  *below* the pretrained baseline on held-out data. It's not shipped — see
  [`docs/measurements/2026-09-02-cycle5-phase3b-finetune.md`](docs/measurements/2026-09-02-cycle5-phase3b-finetune.md)
  for the full writeup, including the negative result.

The methodology behind these — what's measured live vs. one-off, what
counts as a passing threshold, what got walked back after review — is
documented in depth under [`docs/measurements/`](docs/measurements/) for
anyone who wants to see the actual process, not just the summary.

## Roadmap

Built in five cycles, each dropping in behind an existing seam
(`SceneSource`, `PerceptionSource`, `Planner`, `TrafficModel`) without
touching the cycles before it.

| Cycle | Adds | Status |
|---|---|---|
| 1 | Synthetic grid, scripted traffic, ground-truth perception, centerline planner, real-time WS server, native sidecar | **Built** |
| 2 | Real OSM map data, in-app address search, offline caching | **Built** |
| 3 | Traffic-light/stop-sign compliance, lane-level overtaking, reactive IDM/MOBIL traffic, hazard scenarios | **Built** |
| 4 | Real ONNX object detector wired end-to-end (camera → inference → 2D-to-world tracking → scoring) | **Built** — measured zero vehicle detections; ground truth stays the default driver, ML mode is labelled experimental |
| 5 | Sim-generated training data, model fine-tuning, quantization/precision analysis | **Built** — full train/eval pipeline shipped; fine-tuning itself returned a null result (see [Results](#results)) |

Detailed, dated measurement reports and design docs for every cycle live
under [`docs/measurements/`](docs/measurements/) and
[`docs/superpowers/specs/`](docs/superpowers/specs/).
